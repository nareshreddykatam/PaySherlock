# PaySherlock — Safety

PaySherlock can move real money (a Razorpay refund), so this document says
exactly what stops it from doing so incorrectly. Every claim below is
backed by a passing test — see the file paths.

## AI-vs-deterministic boundary

This is the single most important fact for evaluating PaySherlock's
safety: **the LLM is never on the path to a financial decision.**

- The LLM's only two jobs are `provider.plan()` (choose which read-only
  tools to call, from a fixed catalog) and `provider.narrate()` (phrase
  already-decided facts as text) — see
  [`packages/agent/src/runtime`](../../packages/agent/src/runtime).
- Every number in an `InvestigationResult` (root cause, confidence,
  business impact) is computed by deterministic code
  (`packages/agent/src/hypotheses/rules.ts`,
  `packages/agent/src/output/result.ts`) from real tool output — the LLM
  never supplies a number that becomes a stored fact.
- The LLM never calls Razorpay, never touches Postgres directly, and
  never approves or executes anything. `packages/tools`' `executeTool`
  validates every tool call's input/output against a zod schema and scopes
  it to `ToolContext.merchantId` — a field no tool's input schema even
  exposes to the model.
- A `Recommendation` is generated by deterministic code
  (`generateRefundRecommendationCandidate`/`generateNoActionCandidate` in
  `packages/actions`) that reads the investigation's already-decided
  `rootCause`/`targetPaymentId` — it does not ask the LLM "should we
  refund this?".

## The 10 financial-safety guarantees

| #   | Guarantee                                                                       | Enforced by                                                                                                                                                                                                                            |
| --- | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Amounts are integer minor units (paise), never floating point                   | `amountMinorUnits: Int` throughout the schema; no `Float`/`Decimal` amount field exists                                                                                                                                                |
| 2   | A refund can never exceed the payment's refundable balance                      | `validateRefundEligibility` (`packages/actions/src/refund/eligibility.ts`), re-checked against Razorpay's _live_ payment state immediately before executing                                                                            |
| 3   | Refund eligibility is re-validated against live provider state, not cached data | `executeRefund` calls `razorpayClient.payments.fetch()` right before `refunds.create()`                                                                                                                                                |
| 4   | Every financial action requires explicit merchant approval                      | `POST /recommendations/:id/approve` is the only code path that reaches `packages/actions`' refund executor — see [0005-guarded-actions.md](../decisions/0005-guarded-actions.md)                                                       |
| 5   | Every financial action has a mandatory, deterministic idempotency key           | `paysherlock-refund-<recommendationId>` — never random, never per-attempt (`buildRefundIdempotencyKey`)                                                                                                                                |
| 6   | A successful action can never be re-executed                                    | `Action`'s state-machine guard (`markActionExecuting`/`markActionSucceeded`/`markActionFailed` — conditional `updateMany`, `packages/database/src/upsert/action.ts`) refuses `SUCCEEDED → EXECUTING`                                   |
| 7   | A retry reuses the same logical action, never creates a second one              | `retryRecommendationExecution` fetches the existing `Action` row by `recommendationId` and reuses its `idempotencyKey` — see Phase 6 scenario K                                                                                        |
| 8   | Audit events are append-only and immutable                                      | `AuditEvent.create` only — no update/delete path exists anywhere in the codebase                                                                                                                                                       |
| 9   | A provider response is verified before ever reporting success                   | `executeRefund` calls `refunds.fetch()` after `refunds.create()` and only returns `success: true` once the refund's own status confirms it                                                                                             |
| 10  | Double approval can never cause double execution                                | `approveRecommendation`'s atomic conditional `updateMany` (`packages/database/src/upsert/recommendation.ts`) — the second concurrent caller's `updateMany` matches zero rows and returns a `conflict` outcome, never a second `Action` |

## Security checklist

| #   | Check                                                                                  | Status                                                                                                                                                                                                                                          |
| --- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Merchant isolation on every resource (`Payment`/`Issue`/`Recommendation`/`Action`)     | ✅ — every route derives `merchantId` server-side via `resolveMerchant`, never from the client; every query scopes by it. `GET /payments`/`GET /payments/:id` were found _not_ scoped during the Phase 6 audit and have been fixed (see below). |
| 2   | Client cannot supply `merchantId`                                                      | ✅ — no route schema accepts one; a supplied `?merchantId=` query param is ignored (tested explicitly)                                                                                                                                          |
| 3   | Client cannot supply `amount`, `paymentId`, `riskLevel`, or `actionType` for an action | ✅ — the approve/reject/retry endpoints accept no request body at all; every value comes from the persisted `Recommendation`/`Action` row                                                                                                       |
| 4   | LLM has no direct database or Razorpay access                                          | ✅ — see AI-vs-deterministic boundary above                                                                                                                                                                                                     |
| 5   | Webhook signature verification                                                         | ✅ — `X-Razorpay-Signature` HMAC-SHA256 over the _raw_ body, checked before any parsing or DB write (`packages/razorpay`)                                                                                                                       |
| 6   | Financial actions are idempotent                                                       | ✅ — guarantee 5/7 above                                                                                                                                                                                                                        |
| 7   | Double-approval protection                                                             | ✅ — guarantee 10 above                                                                                                                                                                                                                         |
| 8   | Stale-state validation before execution                                                | ✅ — Phase 6 scenario I; `beginRecommendationExecution`'s atomic guard plus live Razorpay re-validation                                                                                                                                         |
| 9   | Audit events are immutable                                                             | ✅ — guarantee 8 above                                                                                                                                                                                                                          |
| 10  | No secrets in logs                                                                     | ✅ — structured logging never includes `RAZORPAY_KEY_SECRET`, `AI_API_KEY`, `RAZORPAY_WEBHOOK_SECRET`, or Authorization headers; error responses carry a safe code/message only, never a stack trace                                            |
| 11  | No secrets in the frontend bundle                                                      | ✅ — only `NEXT_PUBLIC_API_URL` is exposed to the browser; all Razorpay/AI credentials are server-only env vars read exclusively by `apps/api`/`workers/investigator`                                                                           |
| 12  | No production credentials committed                                                    | ✅ — `.env` is gitignored; `.env.example` contains empty placeholders only                                                                                                                                                                      |
| 13  | Errors don't leak implementation details                                               | ✅ — centralized `errorHandler.ts`: `AppError` subtypes return `{code, message}`; unexpected errors return a generic `INTERNAL_ERROR` with no stack trace to the client (logged in full server-side only)                                       |
| 14  | Requests can't hang indefinitely                                                       | ✅ — Razorpay client (10s) and Anthropic provider (30s) both wrap outbound calls in an `AbortController` timeout (Phase 6)                                                                                                                      |
| 15  | Retries can't cause duplicate money movement                                           | ✅ — no automatic retry exists on the financial-action path; `POST /recommendations/:id/retry` is a distinct, merchant-initiated, idempotency-key-reusing action                                                                                |
| 16  | Cross-merchant access attempts are blocked, not just hidden                            | ✅ — a cross-merchant `id` produces a 404 (query-scoped `findFirst`/`findUnique({id, merchantId})`), indistinguishable from "does not exist" — Phase 6 scenario L                                                                               |

### A real finding from this phase, not a hypothetical

The Phase 6 security audit found that `GET /payments` and `GET
/payments/:id` — unlike every other route in the API — did not scope by
merchant at all: any authenticated caller could list or fetch _any_
merchant's payments by id. This has been fixed:
`getPaymentById`/`getPaymentByRazorpayId`
(`packages/database/src/queries/payments.ts`) now require a `merchantId`
and query with it directly (`findFirst({id, merchantId})`, never
fetch-then-check), and both routes resolve the merchant server-side
before calling them. Regression tests for this fix live in
`apps/api/src/__tests__/payments.test.ts`.

## What PaySherlock explicitly does not do

Bulk refunds, payment capture, payment links, settlement automation, or
any autonomous/unapproved financial action. Razorpay is used in **Test
Mode only** — this is an operational/credential discipline (which
`RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET` are configured), not a code-level
"live vs. test" switch. See the root [`README.md`](../../README.md)'s
Security Note and [`AGENTS.md`](../../AGENTS.md) for the full standing
rules.
